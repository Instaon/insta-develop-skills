# insta-api-smoketest

## Purpose

用最小的成本确认"接口是否按文档工作"。不做集成测试、不读业务实现、不依赖真实数据：拿着 `insta-backendApi-docs` 的接口文档，用 curl 发 mock 请求，看返回是否符合文档约定。

本技能是**流程性指导**——它讲清"按什么思路测、守住什么原则"，而具体用哪条 git / curl 命令、怎么推断受影响接口，由你按项目实际情况灵活决定，不要机械套用固定步骤。

## 何时用哪种模式

- **增量测试（默认）**：用户想验证"最近改动相关"的接口、且没提"全量"时。聚焦风险点、省时间。
- **全量测试**：用户明确说"全量 / 所有接口 / 完整回归"时才做。接口多时既慢又易刷屏，不要主动全量。
- **指定接口**：用户点名某些接口时，只测这些。

意图模糊时默认增量，并向用户确认环境即可。

## 流程

### 1. 找到接口文档
先确定测哪个项目（用户指定或当前目录推断），再在对应的 `insta-backendApi-docs` 里找该项目的接口文档（通常是一个 `api_documentation.md`，常以 submodule 形式存在于项目内，或位于平级目录）。项目名和目录名可能不一致，按用户说法尝试匹配；匹配不上直接问，不要猜。

### 2. 从文档提取测试依据
- **base_url**：取文档里按环境列出的地址。默认 `local`（本地服务最安全最快）；用户指定环境时用指定的；`prod` 是线上，任何写操作都可能真实影响数据，必须让用户明确确认后才用。
- **接口清单**：每个接口的方法、路由、请求参数、预期响应结构、错误提示。
- **枚举值**：用于构造合法的 mock 参数，避免传非法值导致误报。

### 3. 确定待测接口
- **增量**：拉取项目最新代码，查看最近提交改动了哪些文件，结合改动的文件、路径、提交信息判断哪些接口可能受影响，再与文档接口对应，得到待测集合。如果改动是通用文件（配置、公共模块等）无法可靠对应到具体接口，**列出候选接口请用户圈定**——既不偷偷全量，也不漏掉风险接口。
- **全量**：仅当用户明确要求时，遍历文档中所有接口。
- **指定**：只测用户点名的接口。

### 4. 用 curl 做黑盒验证
依据文档的请求参数，用 mock 数据（占位值、文档里的合法枚举值）构造请求，对 base_url + 路由发 curl，捕获状态码和响应，对照文档判断：
- 状态码是否符合文档约定（成功 2xx、参数错 4xx 等）；
- 响应是否包含文档描述的字段、结构是否大致对得上；
- 是否出现文档未提及的 5xx / 超时 / 崩溃。

示意（命令细节按实际情况调整，不必照搬）：

```bash
curl -s -o /tmp/resp.json -w "HTTP %{http_code}\n" \
  -X <METHOD> "<base_url>/path" -H "Content-Type: application/json" -d '{...}'
```

原则：只读或无害优先；写操作默认先问用户，或只用明显无害的 mock 值。无需鉴权时不加 header，需要则按文档或用户给的 token 加。

### 5. 给出测试报告
在对话中输出清晰结果，至少包含：环境、模式、测了几个接口；每个接口的方法 / 路由 / 状态码 / 结果（通过 / 与文档不符 / 异常）/ 一句话线索；末尾汇总。对「与文档不符」和「异常」务必给线索（哪个字段、什么状态码、是否像近期改动引起）。

### 6. 失败项的 issue 处置（自主创建 vs 建议）

冒烟失败不等于立刻建 issue。先区分「是不是代码侧契约破坏、是否影响正常使用」，再决定动作。本技能具备**自主提交 issue** 的能力；门槛与 `insta-error-triage` 对齐。

**两条轴同时成立 → 自主创建 issue（无需再等确认）**

1. **确认是代码/实现侧问题**（在 mock 合法、环境正确的前提下，结果稳定可复现，且与文档契约明显冲突——如文档约定 2xx 却稳定 5xx、关键字段缺失/类型错、接口崩溃超时等；不是鉴权未配、服务未起、文档过时、mock 数据不合法）
2. **影响正常使用**（该接口主路径不可用，或核心字段错误会导致调用方无法正常使用）

创建方式：在目标项目用 git remote 确定 `owner/repo`，用 GitHub MCP（或等价方式如 `gh issue create`）直接创建；标题点明接口与现象，正文写清环境、请求要点、实际响应、与文档差异、复现方式；**影响使用时 @Claude01**。创建后在报告中附 issue 链接。

**任一条不扎实 → 只在结论中给 issue 建议，不创建**

例如：偶发失败、分不清是文档过时还是实现 bug、仅边缘参数场景、像环境/鉴权/数据问题、影响面说不清。建议里写清：建议标题、为何建议、不确定点、可选草案正文，方便用户一句「去建」即可执行。

**明确不该建**

服务连不上、prod 未授权写入导致的失败、用户 mock/环境问题等 → 报告里说明，不建议建 issue。

用户明确要求「创建 / 不要创建」时，以用户指令为准。创建失败时输出完整 issue 正文供手动提交，不要假装已创建。

## 原则与边界

- **黑盒**：验证「输入合法 → 输出符合文档」，默认不读业务代码；但为判断「是否确认代码问题」可做最小范围对照（例如确认路由是否存在、是否近期改动相关），不要变成全量排障。
- **mock**：用占位 / 合法枚举值，尽量只读或写无害数据；写操作默认先问。
- **增量是默认，全量需明确**：避免无差别刷屏和无效回归。
- **prod 需确认**：线上数据真实，写操作要用户拍板。
- **服务没起 / 连不上**：报告连接失败，提示先起服务；这不是代码 bug，不建 issue。
- **文档缺失 base_url 或接口对不上**：向用户确认，不要自行假设。
- **自主建 issue 的门槛是「确认实现侧问题 + 影响使用」**；不确定就只建议。

## 与其他技能的关系

- 本技能主责是契约冒烟与失败项的 issue 处置（创建或建议）。
- 若失败项需要更深的日志/代码根因定位（堆栈、kubectl、复杂业务路径），衔接 `insta-error-triage`；两边对 issue 的策略一致：**确认 bug 且影响使用 → 自主建；不确定 → 只建议**。
