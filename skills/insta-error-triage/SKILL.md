# insta-error-triage

## Purpose

接收错误日志后，完成「分析 → 定位 → 分级 → 处置」全流程。本 skill **不直接改代码**；修复是 issue 或报告之后的动作。

核心产出取决于判断是否扎实：

| 判断 | 动作 |
| --- | --- |
| **确认**是代码 bug，**且**影响正常使用 | **自主创建** GitHub issue（@Claude01），创建后把链接告知用户 |
| 不确定（是否代码 bug、是否该建 issue、影响边界不清） | 输出分析报告，并在结论中给出 **issue 建议**（标题 + 草案），**不创建**，由用户决定 |
| 明确不是该建 issue 的问题（噪音、一次性可重试、纯外部依赖抖动等） | 只出报告，说明不建 issue 的理由 |

「自主创建」是能力与默认动作，不是绕过判断——边界不清时宁建议、不创建。

## Workflow

### 1. 日志初步分析

从用户提供的日志中提取关键信息：

- 错误类型与错误消息（异常类名、错误码、HTTP 状态码等）
- 发生时间与频率（一次性、间歇性、持续性）
- 涉及的服务/模块，以及堆栈中的文件与函数名
- 触发路径（哪个接口、哪个任务、哪个消息队列）

信息不足时不要硬下结论，先走后续步骤补上下文。

### 2. 定位目标项目

根据日志与用户说明确定归属项目：

- 用户指定了项目 → 以用户为准，找到代码目录
- 未指定但服务名/模块名能对应 → 先向用户确认
- 无法确定 → 直接问，不要猜

后续代码检索、`acs-config.json`、GitHub 仓库都基于目标项目根目录。

### 3. 结合项目代码定位

用堆栈中的文件名、函数名、错误消息在目标项目检索，理解出错逻辑上下游，并回答：

- 这是**代码缺陷**、配置问题、外部依赖故障，还是数据异常？
- 出错路径在什么条件下被触发？
- 是否已有错误处理/重试被绕过？

「确认是代码 bug」要求能落到具体代码位置或明确的契约/逻辑错误；只能猜、对不上代码时，归入**不确定**。

### 4. 必要时用 kubectl 拉取运行日志

用户给的片段不完整（缺堆栈、缺上下文、想确认频率）时，从目标项目 `acs-config.json` 读 `DEPLOYMENT_NAME` 与 `NAMESPACE`（无则默认 `default`），只读拉取对应服务日志与 Pod 状态（tail / since / previous / get pods / describe 等，按需选用）。

只做只读查询，不重启、不删除、不改集群资源。

### 5. 严重度：是否影响正常使用

只看**是否影响正常功能使用**，不看日志表面级别（ERROR 可能有兜底，WARN 也可能在悄悄丢数据）：

**影响正常使用**（典型）：

- 服务崩溃、CrashLoopBackOff、OOMKilled、启动失败
- 核心接口持续 5xx / 超时，或核心业务流程走不通
- 数据写入失败、数据错乱、消息持续丢失
- 错误高频重复且仍在持续

**不影响正常流程**（典型）：

- 边缘偶发、有兜底，主流程不受影响
- 可重试且重试后成功
- 纯日志噪音、非关键依赖间歇抖动
- 性能变差但功能仍可用

拿不准是否「影响使用」→ 按**不确定**处理（给 issue 建议，不擅自创建）。

### 6. 处置决策（自主创建 vs 仅建议）

完成定位与分级后，按下面两条轴同时成立才自主创建：

1. **确认是代码 bug**（能落到代码位置或明确逻辑/契约错误，而非配置/外部依赖/纯噪音）
2. **影响正常使用**（见第 5 步）

| 情形 | 动作 |
| --- | --- |
| 确认代码 bug **且** 影响正常使用 | → **7a 自主创建 issue**（@Claude01） |
| 确认是缺陷但**不影响**正常使用（可复现、值得跟踪的 backlog） | → **7b 报告 + issue 建议**（不 @Claude01，不创建） |
| 不确定是否代码 bug / 是否影响使用 / 是否该建 | → **7b 报告 + issue 建议**（说明不确定点） |
| 明确不该建（噪音、一次性可重试成功、纯外部故障等） | → **7b 报告**，注明不建议建 issue 及理由 |

用户**明确要求**创建或不要创建时，以用户指令为准（覆盖上表默认策略）。

### 7a. 自主创建 GitHub issue

适用于：确认代码 bug 且影响正常使用。

1. 在目标项目目录用 git remote 确定仓库 `owner/repo`
2. 按《Issue 模板》组织标题与正文，正文中 **@Claude01**
3. 用 GitHub MCP（或当前环境可用的等价方式，如 `gh issue create`）在该仓库**直接创建**，无需再等用户确认
4. 向用户汇报：一句话结论 + issue 链接 + 关键分析要点（让用户知道已建了什么、为何建）

创建失败（MCP 不可用、无权限等）：把本应提交的完整 issue 内容输出给用户，说明需手动提交，并保留「建议立即创建」的明确态度。

### 7b. 输出分析报告（含 issue 建议）

适用于：不确定、或确认缺陷但不影响使用、或不建议建 issue。

按《分析报告模板》输出。若属于「建议创建」分支，在「Issue 建议」中给出：

- 建议标题
- 为何建议 / 为何暂不自主创建（不确定点写清楚）
- 可选：完整草案正文，方便用户一句「去建」即可执行

用户随后同意创建时，再按 7a 的方式创建（是否 @Claude01 按当时是否影响使用决定；backlog 类默认不 @）。

## Issue 模板

标题：`[错误类型] 一句话描述问题与影响`（如 `[5xx] 订单创建接口持续报 NullPointerException，下单不可用`）

正文：

```markdown
## 现象
<错误消息、发生时间、频率、影响的功能>

## 关键日志
<最能说明问题的日志/堆栈片段，控制在 30 行内>

## 初步分析
<定位到的代码位置（文件:行号）、推断的根因、触发条件>

## 建议修复方向
<大致思路，供处理者参考>

@Claude01 请处理这个问题。
```

（若为用户确认后补建的 backlog 跟踪 issue，可省略 @Claude01，并在标题或正文标明非紧急。）

## 分析报告模板

```markdown
## 日志分析报告

### 错误摘要
<错误类型、发生位置、频率、一句话结论>

### 根因分析
<结合代码的具体分析，引用到 文件:行号；若不确定是否代码 bug，写明不确定点>

### 影响范围
<影响哪些功能/用户路径；是否判定为影响正常使用>

### 修复复杂度
<低 / 中 / 高，附一句理由>

### 修复方向
<具体修改思路>

### Issue 处置
<三选一写清楚：
- 已自主创建：附链接与理由（仅当走了 7a 时；7b 不应出现此项）
- 建议创建：建议标题 + 理由 + 可选草案；说明为何未直接创建
- 不建议创建：理由>
```

## Failure Conditions

- 无法判断项目/服务，且当前目录也无法推断：先问用户，不要猜。
- `acs-config.json` 不存在或缺 `DEPLOYMENT_NAME`：跳过 kubectl，仅基于用户日志与代码分析，并在结论中说明上下文不完整。
- 无法创建 issue（工具不可用/无权限）：输出完整 issue 正文供手动提交；该自主创建的不要假装已创建。
- 日志与项目代码完全对不上：向用户确认，不要强行当成本项目 bug 去建 issue。

## Notes

- **自主创建的门槛是「确认代码 bug + 影响使用」**；任一条不扎实 → 只给建议。
- 不确定时的正确姿势是「建议写清楚」，不是「沉默跳过」，也不是「先建了再说」。
- kubectl 只读；重启、回滚、改代码都不属于本 skill。
- 分级看真实影响，不看日志 level 字面。
