# insta-error-triage

## Purpose

接收错误日志消息后，完成"分析 → 定位 → 分级 → 处置"的完整流程。本 skill 的产出只有两种：紧急问题提交 GitHub issue 交给 @ClaudeCode01 处理，非紧急问题输出结构化分析报告。不在本 skill 内直接修改代码——修复是 issue 或报告的后续动作。

**强制规则**：任何情况下，只要分析结论认为"应当创建 issue"（无论紧急与否），必须在本轮输出中向用户明确**提出该建议**（含建议标题与理由），由用户决定是否创建；绝不在未向用户提出/确认的情况下创建，也绝不在建议创建时保持沉默或默默跳过。

## Workflow

### 1. 日志初步分析

从用户提供的日志中提取关键信息：

- 错误类型与错误消息（异常类名、错误码、HTTP 状态码等）
- 发生时间与频率（一次性、间歇性、持续性）
- 涉及的服务/模块，以及堆栈中出现的文件与函数名
- 触发路径（哪个接口、哪个任务、哪个消息队列）

日志信息不足以判断时，不要急着下结论，先走后续步骤补充上下文。

### 2. 定位目标项目

根据日志内容和用户说明，确定这个错误属于哪个项目：

- 用户指定了项目时，以用户指定的为准，找到该项目的代码目录。
- 未指定但日志中的服务名/模块名能对应到某个项目时，先向用户确认再继续。
- 无法确定时，直接问用户，不要猜。

后续的代码检索、读取 `acs-config.json`、确定 GitHub 仓库，都基于目标项目的根目录进行。

### 3. 结合项目代码定位

用堆栈中的文件名、函数名、错误消息文本在目标项目代码中检索，定位到具体代码位置，理解出错逻辑的上下游：

- 该错误是代码缺陷、配置问题、外部依赖故障，还是数据异常
- 出错的代码路径在什么条件下被触发
- 有没有已有的错误处理/重试逻辑被绕过

### 4. 必要时用 kubectl 拉取运行日志

当用户给的日志片段不完整（缺堆栈、缺上下文、想确认频率），从目标项目根目录的 `acs-config.json` 读取 `DEPLOYMENT_NAME` 与 `NAMESPACE`（无 `NAMESPACE` 时默认 `default`），拉取对应服务的日志：

```bash
# 最近日志
kubectl logs deployment/${DEPLOYMENT_NAME} -n ${NAMESPACE} --tail=200

# 按时间窗口
kubectl logs deployment/${DEPLOYMENT_NAME} -n ${NAMESPACE} --since=1h

# Pod 重启过时，看上一个容器的日志（常见于 crash）
kubectl logs deployment/${DEPLOYMENT_NAME} -n ${NAMESPACE} --previous

# 配合 Pod 状态判断是否在 CrashLoopBackOff / OOMKilled
kubectl get pods -n ${NAMESPACE} -l app=${DEPLOYMENT_NAME}
kubectl describe pod <pod-name> -n ${NAMESPACE}
```

只做只读查询，不重启、不删除、不修改任何集群资源。

### 5. 严重度分级

依据"是否影响正常功能使用"判定，宁可保守（拿不准时按紧急处理，或直接问用户）：

**紧急**（影响正常功能）：

- 服务崩溃、CrashLoopBackOff、OOMKilled、启动失败
- 核心接口持续报 5xx、超时，或核心业务流程走不通
- 数据写入失败、数据错乱、消息持续丢失
- 错误高频重复出现且还在持续

**非紧急**（不影响正常流程）：

- 边缘场景的偶发报错，有兜底逻辑，主流程不受影响
- 已知的可重试错误，重试后成功
- 仅日志噪音（如废弃告警、非关键依赖的间歇抖动）
- 性能变差但功能可用

### 6. 处置决策：是否建议创建 issue

完成分级后，先决定"是否建议创建 issue"。这是一个必须显式向用户提出的判断，不得默默跳过：

**建议创建 issue 的情形**
- 紧急问题（见第 5 步分级）→ 建议提交 issue 并 @ClaudeCode01 处理，走 7a。
- 非紧急但已定位到明确根因的缺陷、可复现的已知问题 → 建议创建 issue 跟踪（作为 Backlog，不 @ClaudeCode01），走 7b 的"建议创建"分支。

**不建议创建 issue 的情形**
- 纯日志噪音、一次性可重试成功、已有兜底且不影响功能的边缘偶发报错 → 在报告（7b）中注明"不建议创建 issue"及理由。

无论落入哪一类，只要分析认为应当创建 issue，**必须在本轮输出中向用户明确提出该建议（含建议标题与理由）**，由用户拍板；只有当用户确认后才进入实际创建。

### 7a. 紧急 → 提交 GitHub issue

1. 在目标项目目录下通过 `git remote get-url origin` 确定目标仓库（owner/repo）。
2. 按下方《Issue 模板》组织内容，**先向用户提出创建 issue 的建议、展示标题与正文供确认**（issue 是对外可见的动作，且会触发 @ClaudeCode01 开始处理）。
3. 用户确认后，使用 GitHub MCP 在该仓库创建 issue，正文中 @ClaudeCode01。
4. 输出 issue 链接。

### 7b. 非紧急 → 输出分析报告

按下方《分析报告模板》直接在对话中输出，不创建 issue、不修改代码。若第 6 步判定"建议创建 issue 跟踪"，在报告的"是否建议创建 issue"字段中向用户明确提出该建议（含建议标题与理由），由用户决定是否创建。

## Issue 模板

标题：`[错误类型] 一句话描述问题与影响`（如 `[5xx] 订单创建接口持续报 NullPointerException，下单不可用`）

正文：

```markdown
## 现象
<错误消息、发生时间、频率、影响的功能>

## 关键日志
<最能说明问题的日志/堆栈片段，控制在 30 行内>

## 初步分析
<定位到的代码位置（文件:行号）、推断的根因、触发条件>

## 建议修复方向
<大致思路，供处理者参考>

@ClaudeCode01 请处理这个问题。
```

## 分析报告模板

```markdown
## 日志分析报告

### 错误摘要
<错误类型、发生位置、频率、一句话结论>

### 根因分析
<结合代码的具体分析，引用到 文件:行号>

### 影响范围
<影响哪些功能/用户路径，为什么判定为非紧急>

### 修复复杂度
<低 / 中 / 高，附一句理由（如：只需补一个空值判断 → 低；需要调整重试架构 → 高）>

### 修复方向
<具体的修改思路，改哪个文件、加什么逻辑>

### 是否建议创建 issue
<是 / 否。若是，给出建议标题与一句话理由（如：建议创建 issue 跟踪该空指针缺陷，避免后续回归）；若否，说明为什么不必要>
```

## Failure Conditions

- 用户给的信息无法判断是哪个项目/服务，且当前目录也无法推断：先向用户确认，不要猜。
- `acs-config.json` 不存在或缺 `DEPLOYMENT_NAME`：跳过 kubectl 步骤，仅基于用户提供的日志和代码分析，并在结论中说明上下文不完整。
- GitHub MCP 不可用或无仓库权限：仍须向用户**提出创建该 issue 的建议**，并把本应提交的 issue 内容完整输出给用户，由用户手动提交。
- 日志与当前项目代码完全对不上（可能是别的服务的日志）：向用户确认，不要强行分析。

## Notes

- 分级只看"是否影响正常功能使用"，不看错误日志的表面严重程度——一个 ERROR 级别的日志可能有兜底不影响功能，一个 WARN 也可能意味着数据在悄悄丢。
- kubectl 只做只读操作；任何修复动作（重启、回滚、改代码）都不属于本 skill 的范围。
- 提交 issue 前必须先向用户提出并确认，经用户同意后才创建。
- 任何建议创建 issue 的结论（无论紧急还是非紧急跟踪）都必须显式向用户提出，不得省略、静默跳过或在报告中一带而过。
