# insta-db-crud

## Purpose

在测试库上安全地做数据层面的增删改查，辅助验证功能、构造测试数据、排查数据问题。本技能**只做 DML（数据操作），不做 DDL（结构操作）**——不建表、不改字段、不加索引、不删表。

本技能是**流程性指导**——讲清"按什么原则连接、按什么依据操作、守住什么边界"，具体用什么脚本/命令行方式执行 SQL，由你按项目实际情况灵活选择，不必照搬固定命令。

## 连接方式

- 连接字符串从环境变量 `DATABASE_URL` 读取（PostgreSQL 协议），不要硬编码库名、账号密码到脚本里。
- 主要操作的库/schema 是 `int_app_dev` 下的 `public`；如果用户明确要求操作别的库/schema，以用户说法为准，但要先确认，不要默认切换。
- 执行前确认 `DATABASE_URL` 确实指向测试环境；如果对方向拿不准（比如怀疑是生产库），先向用户确认再执行任何写操作。

## 执行手段

建议用 Node.js（配合 `pg` 包）作为执行 SQL 的载体：写一小段脚本或直接用 `node -e` 之类的方式，连接 `DATABASE_URL`，把要执行的 SQL 传进去，拿到结果后整理输出给用户。具体是写临时脚本文件还是内联执行、是否封装成可复用的小工具，按当次任务体量决定——一次性查询没必要写文件，多次交互或需要复用时再落地成脚本。

核心思路（示意，细节按实际情况调整）：

```js
const { Client } = require('pg');
const client = new Client({ connectionString: process.env.DATABASE_URL });
await client.connect();
const res = await client.query(sql, params);
console.log(res.rows);
await client.end();
```

- 优先用参数化查询（`$1`, `$2` ...）拼接用户输入，避免 SQL 注入。
- 查询结果如果很大，只截取用户关心的部分展示，不要把整表刷屏。

## 操作前先核对字段语义

表和字段的实际用途不能凭猜测。执行任何写操作（增/改/删）前，先确认字段含义和约束：

- 优先看对应项目的 schema 定义（ORM model、migration 文件、schema.prisma、entity 类等，凡是项目里能找到的权威定义都算），确认字段类型、可空性、外键关系、枚举取值范围。
- 如果项目里没有现成的 schema 文档/定义，或字段含义在代码里也说不清楚，向用户确认后再操作，不要臆想字段用途、随意增删字段或编造取值。
- 只读查询（SELECT）如果只是探索性看数据，可以先查再理解，不必等字段语义完全确认；但一旦要做写操作，必须先有依据。

## 操作边界

**允许**：SELECT、INSERT、UPDATE、DELETE，只针对表内数据行。

**禁止**：任何 DDL——`CREATE TABLE`、`ALTER TABLE`、`DROP TABLE`、`TRUNCATE`、建索引、改字段类型等结构性变更。如果任务看起来需要改表结构，停下来向用户说明这超出本技能范围，不要执行。

**写操作前的谨慎**：
- UPDATE / DELETE 尽量先用对应条件跑一次 SELECT，确认命中的行数和内容符合预期，再执行写操作，避免条件写错导致误伤大范围数据。
- 没有 WHERE 条件的 UPDATE/DELETE 极度危险，执行前必须向用户确认这是有意为之。
- 涉及外键关联的删除，先确认是否会破坏引用完整性（比如子表还有依赖数据），必要时向用户说明风险。

## 输出

操作完成后，向用户清楚说明：执行了什么 SQL（或其等价描述）、影响/返回了多少行、关键结果内容。如果是排查性质的查询，顺带给出你从数据里看到的结论或异常点。
