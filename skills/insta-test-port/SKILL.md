# insta-test-port

## Purpose

在团队共用的测试环境端口空间里，**安全地领一个尚未被登记的端口**，并把占用写回 `insta-backendApi-docs` 的注册表，避免多人/多服务联调时撞端口。

本技能是**流程性指导**：讲清「去哪领号、如何保证同步、提交与推送的底线、怎么回报」。具体用哪条 git 命令、怎么解析 YAML，按环境灵活选择，不要机械套用固定脚本。

## 注册表约定（读前先对齐）

权威文件在 `insta-backendApi-docs` 仓库根目录：`test-port-registry.yaml`。

- **`max_used_port`**：当前已占用的最大端口号；新端口 = 此值 + 1。
- **`allocations`**：可选明细，登记每个端口的 `service` / `note`，便于追溯归属。

分配成功后必须同时更新这两处，不能只改数字不记用途。文件头部注释与仓库 README 的「测试端口注册表」小节是约定来源；若与本技能冲突，以仓库内最新约定为准。

## 流程

### 1. 定位可用的 `insta-backendApi-docs` 工作副本

需要一份**可写、且能对远程提交/推送**的仓库副本（不要只读浏览缓存）。按可及性依次尝试，找到即用：

1. 当前项目内的 submodule / 嵌套目录 `insta-backendApi-docs`
2. 与当前项目平级的 `insta-backendApi-docs`
3. 用户工作区中已知的独立克隆（例如常见的 `Documents/Code/insta-backendApi-docs`）
4. 以上都没有 → 向用户确认路径，或按 remote `Instaon/insta-backendApi-docs` 浅克隆一份到合理位置后再用

判据：目录是 git 仓库，且存在（或 pull 后会出现）根级 `test-port-registry.yaml`。子模块若 detached，先切到可推送的跟踪分支（通常是 `main`），再继续。

### 2. 与远程对齐（领号前必须最新）

在该仓库目录拉取最新代码。领号前不同步，很容易和别人刚分配的端口撞车——这是本技能最关键的防冲突手段。

- pull 成功：继续。
- 有本地未提交改动挡路：先处理干净（stash / 确认是否与端口表无关），不要在脏工作区上直接改注册表。
- 完全拉不到远程：说明风险后问用户是否仍用本地现有文件继续（接受可能冲突）；用户拒绝则停止。

### 3. 读取并计算新端口

打开 `test-port-registry.yaml`，解析 `max_used_port`：

- 合法正整数 → 新端口 = `max_used_port + 1`
- 字段缺失、非数字、或文件不存在 → 停止并向用户说明，不要臆造起点端口

若 `allocations` 里已有端口 **≥** 将要分配的新端口，说明表不一致；以「`max_used_port` 与 allocations 中的最大 port」二者的较大者为准再 +1，并在回报里点明曾做过校正。

### 4. 回写注册表

更新同一文件：

1. 将 `max_used_port` 设为新端口
2. 在 `allocations` 追加一条：
   - `port`：新端口
   - `service`：用户指定的服务名 > 当前所在项目名 > 空字符串
   - `note`：用户补充说明，或简短用途（如「本地联调」）；没有就留可识别的占位说明

保持原有注释与 YAML 风格，避免无关重排。不要改动其他已登记项。

### 5. 提交（必须）与推送（尽力）

| 动作 | 要求 |
| --- | --- |
| **本地 commit** | **必须成功**。只暂存注册表相关变更；提交说明写清分配了哪个端口、给谁用。 |
| **push 到远程** | **尽力而为**。网络失败、权限问题等可忽略，**不得因此回滚已成功的 commit**。 |

推送时若因远程已有新提交被拒：优先 `pull --rebase`（或等价同步）后再推一次；若冲突出在注册表本身，按「以较大 max 为准」合并后重新计算是否仍占用当前端口，再提交推送。多次仍失败 → 保留本地 commit，进入回报并标明未推上去。

不要把「push 失败」伪装成「分配失败」——端口已在本地登记并提交，对用户仍然可用，只是团队同步滞后。

### 6. 向用户回报

至少说清四件事：

1. **分配到的端口号**（最醒目）
2. **登记信息**：`service` / `note`（若有）
3. **推送是否成功**（成功 / 失败及简短原因）
4. **注册表路径**（用的是哪份工作副本），便于用户核对

推送失败时补一句：本地已提交，网络恢复后可在该目录再 push，或提醒同事 pull 前注意可能的端口表分叉。

## 原则与边界

- **先同步再领号**：防冲突主要靠 pull，不靠猜。
- **commit 是硬门槛，push 是软门槛**：与用户约定一致——网络差也不能不提交。
- **只动注册表**：不改 `insta-backendApi-docs` 里的接口文档、项目地图等无关文件。
- **一次只领一个端口**：用户要多个时循环「读→写→提交」或在同一次更新里连续递增并写多条 allocation，但每轮仍以最新 `max_used_port` 为基准；不要跳号预留除非用户明确要求。
- **不替用户改业务项目的配置**：本技能只负责注册表领号；把端口写进某服务的 `.env` / 启动参数，除非用户明确要求，否则只回报数字即可。
- **不要「只读查询却改表」**：若用户只要「看看当前最大端口」而未要求分配，只读 `max_used_port` 回报，不写不提交。

## 失败与降级

| 情况 | 处理 |
| --- | --- |
| 找不到任何 docs 仓库 | 问路径或协助克隆，不中止在沉默里 |
| 注册表损坏 / 无 `max_used_port` | 停止，展示文件问题，请用户修复后再领 |
| 工作区脏且与注册表无关 | 先整理再改，避免裹进无关 diff |
| commit 失败 | 视为分配未完成，不要把端口当已占用回报 |
| push 失败 | 端口仍有效；明确告知未同步远程 |
| 并发导致远程注册表已前进 | 同步后按新的 max 重算；若你本地端口已被别人占用，改用更新后的 +1 并说明 |

## 与其他技能的关系

- 领到端口后若要写接口文档里的 local base_url，属于文档维护，可衔接对 `insta-backendApi-docs` 的常规文档更新，不在本技能强制步骤内。
- 冒烟测试（`insta-api-smoketest`）默认连已有服务地址；只有用户要「先占个新端口再起服务再测」时，先本技能再测。
